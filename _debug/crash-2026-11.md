# 闪退诊断（2026-11-09）

> 结论先行：**不是硬件/显卡问题，也不是我们的两个 mod。**
> 10-20 到 11-09 事件查看器里有 **25 次** `isaac-ng.exe` 崩溃，其中 **16 次能精确落到
> 3 个第三方 mod 的 Lua 行号**；剩下 4 次是我们的 mod（10-22 前，已修）+ 4 次堆损坏 + 1 次已卸载的 run-chronicle。
> 而且**除退出崩溃外的 9 次，全都发生在"开新局 → 第一层起始房"的那几秒**。

## 2. 三个主犯的代码位置

### A. benighted soul 0.11.6.0 —— 5 次，开新局必崩风险

`ibs_scripts/commons/classes/marks.lua`：

```lua
113 function self:RemoveTheLockedFromPool(isContinue)
114   if not isContinue then
115     local itemPool = game:GetItemPool()
...
124     if v.Trinkets then            -- 饰品
125       for _,id in pairs(v.Trinkets) do
126         itemPool:RemoveTrinket(id)   -- ← 崩在这
...
133 self:AddPriorityCallback(ModCallbacks.MC_POST_GAME_STARTED, CallbackPriority.IMPORTANT, 'RemoveTheLockedFromPool')
```

- 触发时机 = `MC_POST_GAME_STARTED`（开局池子清洗），优先级 `IMPORTANT`。
- `id` 来自 `IBS_TrinketID.*`，是 `Isaac.GetTrinketIdByName("...")` 拿到的**自定义饰品 id**
  （见 `id_item&trinket&pocket.lua:208+`）。
- 同一个 mod 的 `AvoidLockedTrinkets`（`MC_POST_GET_COLLECTIBLE`）也调 `RemoveTrinket`，是第二个雷。

### B. retribution 1.39 —— 4 次，开新局

`lua/features/items/training_seat.lua`：

```lua
23 mod:AddCallback(ModCallbacks.MC_POST_EFFECT_INIT, function(_, effect)
25   mod.ForAllPlayers(function(player)
26     ... player:GetTrinketMultiplier(mod.TRINKETS.TRAINING_SEAT)  -- ← 崩在这
27   end)
```

- `mod.TRINKETS` 就是 `mod.Trinket`（`items.lua:477`），值同样是 `Isaac.GetTrinketIdByName("Training Seat")`。
- 另一次崩在 `lua/utilities/manager_itemstate.lua(38)` 的 `player:GetData()`——同一类"玩家对象失效"。
- 三次 `GetTrinketMultiplier` 崩在**三个不同偏移**（0x48B588 / 0x38D73E / 0x33B396），
  说明不是"一条指令空指针"那么简单，更像同一处逻辑在不同数据下踩到不同的坏内存。

### C. heaven's call 1.6.11 —— 7 次，只在退出游戏

`scripts/libs/save_manager.lua`：

```lua
321 function SaveManager.Utility.GetListIndex()
323   local roomDesc = game:GetLevel():GetCurrentRoomDesc()   -- ← 崩在这
324   local listIndex = roomDesc.ListIndex
```

- 日志里崩溃前必有 `Isaac is shutting down...` + `delete N rooms.`：**房间正在被删除**，
  `GetCurrentRoomDesc()` 返回的 desc 已经失效，读 `ListIndex` 就崩。
- 偏移固定 `0x30E2D0`，7 次完全一致 → 100% 确定是这个调用。
- **影响最小**：发生在关机流程里，存档已经写完（`Saving PersistentGameData to Steam Cloud` 在前），
  只是退游戏时弹个崩溃框。

### 共同可疑点（推测，未定论）

前两个 mod 都在"开新局"时把 **mod 自定义饰品 id** 传给引擎 C 接口
（`ItemPool:RemoveTrinket` / `EntityPlayer:GetTrinketMultiplier`）。
REPENTOGON 的自定义饰品 id 不在原版 0~187 区间，如果引擎这两个函数内部按原版 id 做数组下标，
就会越界——这能同时解释"读野地址"和 §3 的堆损坏。**这条要 mod 作者确认，不是我们能改的。**

## 5. 怎么验证（三步，约 20 分钟）

> 关 mod 不用开游戏：在 mod 目录里放一个空的 `disable.it` 即可；删掉就恢复。

```powershell
$Mods = 'D:\LenovoSoftstore\Install\Steam\steamapps\common\The Binding of Isaac Rebirth\mods'

# 关掉 benighted soul
New-Item -ItemType File "$Mods\benighted soul_3290493485\disable.it" -Force

# 恢复
Remove-Item "$Mods\benighted soul_3290493485\disable.it"
```

1. **先关 benighted soul**，连开 3 局新档（不同角色），看还崩不崩。
   - 不崩 → 结案，去工坊留言/等更新；它是"开局就死"的那个，优先级最高。
2. **再关 retribution**（`retribution_2881008017`），打 2 层 + 用几次主动道具。
3. heaven's call 的退出崩溃**可以不管**（不丢进度）。想彻底消掉就关它。

每轮结束后这样查有没有新崩溃（30 秒）：

```powershell
# 最近一次崩溃日志的尾巴
Get-ChildItem "$env:USERPROFILE\Documents\My Games\Binding of Isaac Repentance" -Filter 'isaacv*.txt' |
  Sort-Object LastWriteTime -Descending | Select-Object -First 1 |
  ForEach-Object { $_.LastWriteTime; Get-Content $_.FullName -Tail 12 }

# 有没有新的 Application Error
Get-WinEvent -FilterHashtable @{LogName='Application'; Id=1000; StartTime=(Get-Date).AddHours(-2)} |
  Where-Object Message -match 'isaac-ng' |
  ForEach-Object { "$($_.TimeCreated)  " + (($_.Message -split "`n")[2]) }
```

**如果关掉两个 mod 还崩在别的 mod 上** → 说明是"开新局时的共同初始化"在破坏内存（§2 猜测），
那就按 `_debug/render-target-flood.md` 那套二分法，一次关一半（每次只放 `disable.it`，别删文件）。

## 6. 不是硬件的依据

- 全部崩溃都是 `isaac-ng.exe` / `Lua5.4.dll` / `ntdll.dll` 里的 `0xC0000005`、`0xC0000374`，
  **没有一次是 `nvlddmkm` / 显卡驱动超时 / WHEA 硬件错误**。
- 近 60 天 System 日志：只有 9-12 有两次 `Kernel-Power 41`（非正常关机），10 月以后没有。
- 显卡驱动 `NVIDIA 591.59`，OpenGL 4.6 初始化正常；同一次会话能连玩 93 万行日志（10-26）才崩，
  不是"一进游戏就掉"的驱动/显存症状。

累计：benighted soul **7** 次、heaven's call **7** 次、retribution **4** 次、堆损坏 **5** 次。

**11-13 这次的特殊点：`.txt` 是 0 字节。**
REPENTOGON 只写出了 21 MB 的 `.dmp`，没写出日志副本；在 dump 里也搜不到 `Lua stack trace` /
`marks.lua` / `[HIGHLIGHT]` 这些字符串（只有模块的符号表，例如 `Entity_Player::TryRemoveTrinket`
是导出名列表里的一条，**不是**崩溃现场证据）。所以这次只能靠**偏移认人**：
`0x301D4C` 和 11-09 11:59、10-20/10-21/10-22 那 5 次完全一致，而那 5 次的 Lua 栈都明确写着
`[C] RemoveTrinket ← benighted soul/marks.lua(126)`。

**后果评估：这次没丢数据。** `data\highlight-review\save3.dat` 的 mtime 仍是 11-12 20:20:52，
说明崩溃发生在任何检查点写盘之前（和"开新局 `MC_POST_GAME_STARTED` 里崩"一致），
不存在写了一半的存档——外部快照（`_logs\save-backup\`）也一直是"未变"。

**结论不变：** 想让"开新局闪退"消失，第一步就是关掉 `benighted soul_3290493485`（放 `disable.it`），
连开几局新档验证。
